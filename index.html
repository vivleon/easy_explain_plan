01. 서비스·개발 계획

1. 서비스 정의 — 팀 설계안

EasyExplain은 학습자가 모르는 개념을 질문하고, 설명 수준을 바꾸며, 후속 질문으로 이해를 넓히는 챗봇입니다. 첫 버전은 한국어 중심, 텍스트 입력·텍스트 응답만 제공합니다. 이름의 상표·도메인 사용 가능 여부는 확인하지 않았습니다.

항목 설계
대상 개발 공부 입문자·일반 학습자
핵심 질문 “API가 뭐야?”, “아까 설명을 더 쉽게 해줘.”
설명 수준 easy 아주 쉽게 / beginner 입문자 / advanced 전공자
기본 답변 구성 한 줄 정의 → 쉬운 설명·비유 → 짧은 예시 → 핵심 정리
후속 버튼 더 쉽게 / 예시 하나 더 / 핵심만: 같은 채팅 API로 질문 전송
기록 로그인한 본인의 대화 목록·상세 보기
제한 최신 검색 결과나 검증된 전문 자문을 제공하는 서비스가 아님

“아주 쉽게”는 설명 난이도이며, 아동 개인정보를 수집하는 별도 아동 서비스로 설계하지 않습니다. 의료·법률·투자 판단 기능은 범위에 넣지 않습니다. AI 설명의 오류 가능성을 화면에 알립니다.

2. 범위 구분

과제 필수: FastAPI 웹 UI, 회원가입·로그인·접근제어, 서버 AI 호출, 문맥 유지, 사용자별 질문·응답·시각 DB 저장과 조회, 서버 이벤트 로그, 입력 검증, AI 오류·타임아웃 처리, 외부 접속 URL, 브랜치·PR·개인별 유의미한 커밋 10회 이상, 기술 문서. [S0: 2~4쪽]

이번 주제의 기본 기능: 설명 수준 3가지, 새 대화, 후속 질문, 내 대화 목록·상세, 응답 대기 표시·중복 클릭 방지. 이것들은 과제가 지정한 기능이 아니라 팀이 선택한 구현 방식입니다.

일단 제외: PDF 업로드, RAG·벡터 DB, 웹 검색, 음성, 이미지, 자동 퀴즈 채점, 결제, 소셜 로그인, 실시간 스트리밍, 모바일 앱, 다중 AI 에이전트. 필수 검증이 끝난 뒤에도 기능 확대보다 안정화를 우선합니다.

4. 120시간 학습 블록에 맞춘 일정 예시

원문 1쪽에는 학습시간 120시간이 표기되어 있으나 달력상 일수와 인당/팀 공수 해석은 명시되어 있지 않습니다. 아래는 8시간×15회차의 팀 진도표 예시입니다. 실제 수업·제출일에 맞춰 회차를 배치합니다. 각 회차에서 네 명이 담당 범위를 병렬로 진행하며, 아래 시간을 네 명의 합산 개발 공수로 읽지 않습니다.

회차 시간 목표 통과 조건
1~2 16h 저장소·규칙·계약·실행 뼈대 네 명 로컬 /health, API·DB v1 합의; 가능하면 공개 /health 선배포
3~5 24h 인증/DB, AI 모의 구현, UI 병렬 각 모듈 테스트, PR 반영; UI는 고정 응답으로 먼저 연결
6~8 24h 로그인→질문→응답→저장 통합 실제 AI 1회 이상, 후속 질문 문맥 유지, 내 기록 조회
9~11 24h 오류·권한·입력·DB 회귀검증 타인 대화 차단, 타임아웃·DB 실패 테스트, 모바일 화면 점검
12~13 16h 배포 안정화·문서·증빙 외부 URL, 재시작 후 DB 보존, README만으로 실행
14~15 16h 발표·커밋 점검·수정 여유 네 명의 설명 가능성, 테스트 증거·PR·커밋 교차 확인
합계 120h

배포를 마지막 날 처음 시도하지 않습니다. 초기에는 /health만 확인하고, 기능 완성 이후 같은 배포 경로를 검증합니다. 필수 경로가 지연되면 디자인 장식·추가기능을 먼저 줄이고, 문맥/로그/인증/배포는 줄이지 않습니다.

5. 1일 운영 방식

시작 10분: 어제 결과·오늘 이슈·막힌 의존성만 공유합니다. 구현 중: 한 사람당 진행 중 이슈 1개, 이슈당 Codex 작업 세션 1개를 기본으로 합니다. 중간: 공유 API/DB 변경이 생기면 코드보다 계약 변경 PR부터 올립니다. 종료 전: 담당자는 실행한 테스트 결과와 다음 사람에게 필요한 변경점을 이슈/PR에 기록합니다. 팀장은 일정·통합을 조정하지만 다른 세 사람의 구현을 대신 완성하지 않습니다.

02. 팀 배분·GitHub 운영

1. 책임과 결과물

역할 주 책임 주 작업 파일 주요 산출물 기본 리뷰어
L 팀장 공통 구조, 계약, CI, 통합, 배포 app/main.py, app/core/, tests/integration/, .github/, 배포 설정 실행 뼈대·공통 오류·통합테스트·URL·제출 묶음 A 또는 B
A 팀원1 회원·세션·권한, DB·기록 app/db/, app/auth/, app/conversations/ 인증 API·DB·내 기록 API·DB 확인 가이드 B, 보안/스키마는 L 추가
B 팀원2 AI 호출, 프롬프트, 문맥·오류 app/chat/ 실제/모의 provider·채팅 API·AI 테스트 A
C 팀원3 웹 화면, API 연결, 사용성 app/web/, app/templates/, app/static/ 로그인·챗·내 기록·반응형·화면 테스트 L 또는 A

테스트도 담당 영역과 함께 소유합니다: A=tests/auth·conversations, B=tests/chat, C=tests/web, L=tests/integration·공통 conftest. 각자 기여 문서는 별도 파일로 작성합니다.

팀장은 관리자만 하는 역할이 아닙니다. 실제 공통 코드·테스트·배포 작업을 맡습니다. AI 담당자는 인증이나 DB를 다시 만들지 않습니다. A가 제공한 인증 의존성과 저장소 함수를 호출합니다. UI 담당자는 키를 다루거나 사용자 소유권을 브라우저만으로 판단하지 않습니다.

2. 선행 합의와 충돌 방지

EE-02에서 API 요청/응답, 오류 코드, 테이블 필드, 내부 함수 경계를 v1로 합의합니다. L이 뼈대의 파일을 만든 이후 구현 소유권은 위 표를 따릅니다. 모든 사람이 app/main.py나 models.py를 동시에 고치지 않습니다. 공유 파일(main.py/config.py/conftest.py/API 계약/의존성 파일) 변경은 L이 조정하고 리뷰합니다. 소유권은 작업 약속이며 CODEOWNERS만으로 편집이 기술적으로 금지되는 것은 아닙니다.

다른 영역의 변경이 필요하면 의존성 이슈를 작성합니다. 이미 누군가 작업 중인 파일을 덮어쓰거나, 전체 프로젝트 재생성·reset --hard·force push·테스트 삭제로 해결하지 않습니다.

3. 저장소와 브랜치

저장소는 프로젝트용 하나를 사용합니다. 기존 다른 프로젝트 저장소를 임의로 재사용하지 않습니다. 네 명은 각자의 GitHub 계정으로 참여합니다. GitHub 계정 비밀번호나 API 키를 공유하지 않습니다.

main  : 리뷰와 테스트를 통과한 기준 코드
  ├─ chore/ee-02-bootstrap
  ├─ feat/ee-08-auth-session
  ├─ feat/ee-13-chat-ai
  ├─ feat/ee-12-chat-ui
  └─ fix/ee-18-integration

작업 흐름: 이슈 선택 → 최신 main → 기능 브랜치 → Codex 구현 → 본인 검증 → 커밋 → PR → 다른 사람 리뷰 → CI → Merge commit. 첨부는 main/develop 분리 또는 그에 준하는 운영을 허용하므로, 소규모 팀은 main+기능 브랜치로 단순화합니다. [S0: 4쪽]

최초 브랜치 생성을 위한 README/규칙 등 최소 초기 커밋 1회는 예외로 기록할 수 있습니다. 그 이후 구현은 모두 PR로 반영합니다. main 직접 push를 일상 작업으로 사용하지 않습니다.

4. 개인별 10개 이상 유의미한 커밋

과제는 구성원별 유의미한 커밋 10회 이상과 실제 이력에 맞는 작업 요약을 요구합니다. [S0: 4~5쪽] 운영 목표는 개인별 12개 안팎의 독립적인 검증 가능한 변경입니다. 6개 이슈에 기능·테스트·보완이 자연스럽게 나뉠 수 있으나, 기계적으로 이슈당 2개를 강제하지 않습니다. 단순 공백·빈 커밋·의미 없는 파일 분할로 수를 채우지 않습니다.

역할 유의미한 변경 단위 예시 12개
L 초기 규칙, FastAPI 뼈대, 설정 검증, API 계약, request_id, 오류 처리, CI, 통합 로그인 테스트, 통합 대화 테스트, 배포 설정, 재시작 검증, 제출 문서
A 사용자 모델, 대화 모델, 비밀번호 해시, 가입, 로그인, 세션 만료, 로그아웃 무효화, 소유권 검증, 대화 조회, 저장 실패 처리, DB 확인 스크립트, 백업/복구 검증
B provider 경계, Fake provider, 수준별 프롬프트, 최근 대화 구성, 실제 API 호출, 질문 처리 연결, 타임아웃, 상위 API 오류 매핑, 중복 요청 정책, 사용량 가드, 문맥 테스트, 실 API 검증 기록
C 기본 레이아웃, 가입 UI, 로그인 UI, 질문 입력, 수준 선택, 응답 표시, 후속 버튼, 대기/중복전송 처리, 오류 안내, 내 기록 목록, 모바일/키보드 개선, 화면 테스트/문서

병합 방식은 Create a merge commit을 권합니다. 이 방식은 브랜치의 개별 커밋을 보존하고, Squash and merge는 PR의 여러 커밋을 기본 브랜치의 한 커밋으로 합칩니다. [S1] 따라서 이 과제에서는 Squash를 사용하지 않는 편이 기여 증빙에 유리합니다. “Require linear history”는 Merge commit과 맞지 않으므로 동시에 켜지 않습니다. [S2]

# 저장소 안에서, 본인의 확인된 정보로만 설정
# 다른 사람의 이름/이메일로 작성자를 바꾸지 않는다.
git config --local user.name "본인 이름"
git config --local user.email "본인의 GitHub 연결 이메일"

# 제출 전 main에 도달 가능한 개별 커밋을 점검
# 숫자만으로 유의미함을 판정하지 않고 diff/이슈/PR을 함께 본다.
git fetch origin
git shortlog -sne --no-merges origin/main
git log --no-merges --format='%h %aN <%aE> %s' origin/main

Codex 클라우드/앱의 작성자 표시를 이름만 보고 신뢰하지 말고, 실제 git author·PR 작성자·작업 기록을 확인합니다. 가장 단순한 운영은 각자 로컬 복제본에서 Codex를 이용하고 본인이 확인한 변경을 자신의 계정으로 커밋하는 것입니다.

5. 보호·리뷰·보드

설정 가능한 저장소에서는 main에 PR 필수, 다른 사람 1명 승인, CI 통과, 대화 해결, force push/삭제 금지를 설정합니다. L의 PR은 A 또는 B가 승인합니다. 보안·DB 계약 변경은 L이 추가 검토합니다. 브랜치 보호 기능의 제공 범위는 GitHub 요금제·공개/비공개 여부에 따라 다릅니다. [S2] 사용 불가 시 무료로 된다고 단정하지 말고, 가능한 설정과 수동 승인 기록을 문서에 남깁니다.

GitHub 보드 상태는 Backlog / Ready / In progress / Review / Done의 다섯 개면 충분합니다. 24개 이슈의 고정 코드 EE-01~EE-24는 실제 GitHub 이슈 번호가 아닙니다. PR에는 등록 후 실제 번호로 Closes #실제번호를 씁니다.

PR 완료 조건: 요구사항 충족, 담당 테스트와 회귀 테스트 통과, 실행한 명령/결과 기록, 민감정보 없음, 문서 변경, 작성자가 주요 코드를 설명할 수 있음, 타인 리뷰 승인.

6. Codex 운용

루트 AGENTS.md에 공통 규칙을 둡니다. Codex는 AGENTS.md를 프로젝트 지침으로 읽을 수 있습니다. [S3] GitHub Codex 리뷰 연결·권한 설정을 완료한 저장소에서는 PR에 @codex review로 검토를 요청할 수 있습니다. [S4] 봇 리뷰는 팀원의 실제 리뷰와 기능 검증을 대체하지 않습니다.

한 PC에서 병렬 작업해야 할 때는 별도 clone 또는 Git worktree를 사용하고, 각각 별도 작업 브랜치로 관리합니다. Codex의 worktree 기능도 독립 작업용으로 제공됩니다. [S5] 하지만 한 사람이 에이전트 4개를 돌리는 것은 4명의 협업 기여를 자동으로 충족하지 않습니다.

04. API 계약 v1 — 코드 작성 전에 합의

이 문서는 팀 설계안이며 실제 구현된 API를 설명하는 문서가 아닙니다. 같은 출처의 웹과 JSON API를 사용합니다. user_id는 요청 본문에서 받지 않고 서버 인증으로 결정합니다. 시각은 ISO 8601 UTC, 목록은 최신순·상세 턴은 오래된 순서로 표시합니다.

1. 페이지

경로 접근 담당

GET /signup 공개 C
GET /login 공개 C
GET /chat 로그인, 아니면 로그인 페이지로 303 이동 C+A
GET /history 로그인, 아니면 303 이동 C+A
GET /health 공개, 키·DB 경로·개인정보 출력 금지 L

API의 비로그인 요청은 HTML 리다이렉트가 아니라 JSON 401을 반환합니다.

2. API

메서드·경로 요청 성공 인증/담당
POST /api/auth/signup email, password 201: user.id, email 공개·Origin 검증 / A
POST /api/auth/login email, password 200: user + csrf_token, 세션 쿠키 설정 공개·Origin 검증 / A
GET /api/auth/me 없음 200: user + csrf_token 로그인 / A
POST /api/auth/logout 없음 204, 세션 무효화·쿠키 삭제 로그인+CSRF / A

limit 기본 20·최대 100. 존재하지 않거나 타인 소유인 대화는 같은 404 응답을 사용합니다. 읽기 결과에도 password_hash, token_hash, 타인의 개인정보를 포함하지 않습니다. 로그인 후 상태 변경 요청에는 X-CSRF-Token 헤더를 사용합니다.

{

성공 응답:

{
  "request_id": "서버가 발급한 추적 ID",
  "turn_id": 31,
  "conversation_id": "9b1c4da5-7a74-4f97-88cb-1b2790e510a9",

    "code": "AI_TIMEOUT",
    "message": "응답이 지연되고 있어요. 잠시 후 다시 시도해 주세요.",

HTTP code 설명
401 AUTH_REQUIRED 비로그인·만료

404 CONVERSATION_NOT_FOUND 없는 대화 또는 타인의 대화
409 ACCOUNT_EXISTS 이미 등록된 이메일
409 CHAT_BUSY / REQUEST_CONFLICT 처리 중 또는 같은 키의 다른 내용
422 VALIDATION_ERROR 빈 입력·길이·잘못된 level/UUID
429 RATE_LIMITED 우리 서비스의 요청 한도

L의 공통 예외 처리기가 오류 JSON 형식을 통일합니다. FastAPI 기본 검증 오류도 같은 규격으로 매핑합니다. 상위 API의 원문 오류, 비밀 값, 스택 트레이스는 사용자에게 보내지 않습니다.

5. 중복·재시도·순서

클라이언트는 전송할 때 UUID를 만들고 응답 대기 중 버튼을 비활성화합니다. DB의 (user_id, client_request_id) 유일 제약으로 동일 요청을 식별합니다.

  • 같은 키+같은 내용+완료: 저장된 결과를 반환하고 AI를 다시 호출하지 않습니다.
  • 같은 키+다른 내용: 409 REQUEST_CONFLICT.
  • 같은 키+처리 중: 409 CHAT_BUSY. 자동 재전송하지 않습니다.
  • 같은 키+실패: 기존 실패를 돌려줍니다. 사용자가 명시적으로 다시 시도할 때만 새 키를 생성합니다.

첫 버전은 단일 worker/인스턴스에서 사용자별 진행 중 요청을 제한합니다. 여러 창에서 다른 질문을 동시에 보낼 때도 순서가 섞이지 않도록 409를 반환하는 단순 정책을 사용합니다. 프로세스 재시작 중 결과가 불명확한 요청은 자동으로 재호출하지 않고 확인 후 재시도하게 합니다.

05. DB·인증·안전 설계

1. 테이블 4개

테이블 핵심 필드 목적
users id, email(unique), password_hash, created_at 회원
auth_sessions id, user_id(FK), token_hash(unique), csrf_token, created_at, expires_at 서버에서 취소 가능한 로그인 세션
conversations id(UUID), user_id(FK), title, created_at, updated_at 사용자별 대화 묶음
chat_turns id, conversation_id(FK), user_id(FK), client_request_id, request_id, level, question, answer(nullable), status, error_code(nullable), created_at, completed_at(nullable) 질문·응답·상태·추적

chat_turns의 (user_id, client_request_id)에는 유일 제약을 둡니다. conversations.user_id, chat_turns(conversation_id, created_at, id), auth_sessions.token_hash 조회를 지원합니다. chat_turns.user_id는 대화 소유자와 일치해야 하며 서버 저장소 함수에서 강제합니다. 필요 시 SQLite 외래키 제약을 명시적으로 활성화하고 테스트합니다.

    users ||--o{ chat_turns : creates

과제 최소 필드는 사용자 식별·생성 시각·질문·응답입니다. 추가 테이블·상태·요청 ID는 팀 설계입니다. [S0: 3쪽] 학습용 테스트 DB와 실제 평가 DB를 분리합니다. schema를 바꿀 때 운영 DB를 지워서 해결하지 않습니다. 초기 DB 생성과 스키마 변경은 다르므로, 스키마 변경 필요 시 A가 백업 및 명시적인 변경 절차를 마련합니다.

2. 인증 정책

비밀번호는 평문·복호화 가능한 암호문으로 저장하지 않고 검증된 해시 라이브러리를 사용합니다. 제안은 pwdlib의 Argon2 지원입니다. FastAPI 보안 문서의 비밀번호 해시 설명을 참고하되, 그 문서의 JWT 전체 구조를 이 과제에 그대로 추가할 필요는 없습니다. [S8]

가입: 이메일 형식/정규화/중복과 비밀번호 10~128자 검증을 수행합니다. 비밀번호 자체는 trim하지 않습니다. 로그인 성공: 표준 난수 생성기로 충분히 긴 세션 토큰을 만들고, DB에는 토큰 해시·사용자·만료를 저장합니다. 브라우저에는 불투명 토큰만 HttpOnly 쿠키로 전달합니다. 쿠키는 운영 HTTPS에서 Secure, SameSite=Lax, Path=/로 설정합니다. 서버는 토큰 해시 조회와 만료를 매 요청 확인합니다. 로그아웃하면 DB 세션을 지워 재사용을 차단합니다. 프로젝트 기본 세션 만료는 2시간으로 제안합니다. 이 수치는 원문 요구가 아닙니다.

로그인 뒤 쓰기 요청은 세션 연계 CSRF 토큰을 헤더로 검증합니다. 로그인/가입을 포함한 쓰기 요청은 JSON만 받고 허용된 Origin을 확인합니다. 다른 출처의 CORS를 열지 않습니다. SameSite만을 유일한 방어로 삼지 않습니다. [S9]

3. 권한·비용·개인정보

모든 대화 조회/전송은 인증 사용자와 소유자를 동시에 확인합니다. 화면에서 버튼을 숨기는 것은 권한 검사가 아닙니다. 다른 사용자 ID를 본문에 넣어도 저장 대상이 바뀌면 안 됩니다. 사용자별 진행 중 질문 1개, 분당 호출 수, 하루 전체 호출 시도 수를 설정 가능하게 둡니다. 예시값은 10회/분/사용자, 200회/일/서비스이며 예산·평가 인원에 맞춰 조정합니다. 한도는 요금 상한을 정확히 보장하지 않으므로 AI 제공자 사용량도 확인합니다.

화면에 대화가 DB에 저장되고 AI 제공자에게 전송된다는 안내를 둡니다. 실제 이름·전화번호·계정 비밀번호·개인 문서 대신 학습용 개념 질문으로 시연합니다. 테스트·발표 캡처에 세션 토큰, 실제 이메일, 키, 운영 DB 내용을 노출하지 않습니다.

4. 저장·오류 정책

  1. 검증을 통과한 요청은 pending 상태로 질문을 저장하고 commit합니다.
  2. DB 연결/쓰기 트랜잭션을 붙잡은 채 AI를 기다리지 않습니다.
  3. AI 성공 후 answer/completed_at/status=completed를 저장합니다.
  4. AI 실패는 status=failed와 안전한 error_code를 저장하고 사용자에게 오류를 안내합니다.
  5. DB 장애는 rollback·db_save_failed 로그·503으로 처리합니다. 저장되지 않았는데 저장됐다고 말하지 않습니다.
  6. 서버 재시작으로 남은 오래된 pending은 최대 요청 처리시간보다 넉넉한 기준으로 점검하여 interrupted 실패 상태로 정리합니다. 자동 유료 재호출을 하지 않습니다.

5. 로그

필수 이벤트: request_received / ai_call_start / ai_call_success 또는 ai_call_failed / db_save_success 또는 db_save_failed. 서버 request_id로 같은 요청을 연결합니다. [S0: 3, 5쪽]

INFO request_received request_id=... user_id=12 path=/api/chat
INFO ai_call_start request_id=... user_id=12 model=...
INFO ai_call_success request_id=... latency_ms=1240
INFO db_save_success request_id=... user_id=12 turn_id=31

본문·쿠키·Authorization·API 키·비밀번호는 서버 로그에 남기지 않습니다. 질문·응답 원문 저장은 접근 통제된 DB에서만 수행합니다. 대화 로그와 운영 로그는 목적이 다릅니다.

6. DB 검증·백업

A는 scripts/check_logs.sql 또는 동일 목적의 Python 스크립트를 구현합니다. 예시 쿼리(실제 DB 스키마에 맞춰 검증 후 문서화):

SELECT id, user_id, conversation_id, created_at, level,
       question, answer, status, error_code
FROM chat_turns
WHERE user_id = :user_id
ORDER BY created_at DESC, id DESC
LIMIT 20;

대화 내용이 있는 실제 DB 파일을 Git에 올리지 않습니다. 평가자는 본인 계정의 API/화면 또는 팀이 허용한 내부 스크립트로 확인합니다. 전체 DB를 공개 URL로 제공하지 않습니다. 가동 중 SQLite 백업은 Python sqlite3의 backup API 등 일관된 백업 방법을 사용합니다. [S10] 운영 DB 위에 즉시 복구하지 말고, 복사한 테스트 경로에서 먼저 복구를 검증합니다.

06. AI·설명 품질 명세

1. 최소 구성

AI provider 인터페이스 하나를 두고 FakeAIProvider와 실제 provider 하나만 구현합니다. 제안 실제 provider는 OpenAI Responses API입니다. 모델은 프로젝트에서 사용 가능한 것을 확인하여 AI_MODEL 설정으로 선택하고, 운영 코드에 모델명을 여러 곳에 하드코딩하지 않습니다. OpenAI 텍스트 생성 공식 문서를 구현 기준으로 사용합니다. [S11]

Codex는 개발을 돕는 도구이고, EasyExplain의 사용자 질문에 응답하는 AI API는 별도 구성 요소입니다. 개발 도구 로그인만으로 서비스 서버의 AI 키가 자동 준비되었다고 가정하지 않습니다. API 키 준비에는 제공된 보안 설정 흐름을 사용합니다. 키를 채팅·이슈·커밋·문서에 붙여넣지 않습니다.

자동 테스트와 Codex 작업환경은 Fake provider를 기본으로 합니다. 실제 키 없이도 인증·UI·저장·오류를 개발하게 합니다. 운영은 Fake provider로 기동하지 못하게 설정 검증을 추가하고, 개발 화면에는 모의 응답임을 표시합니다. Fake 통과를 실제 AI 연동 완료로 보고하지 않습니다.

2. 내부 계약 예

# 구현 시 app/chat 내부에서 구체적인 타입을 확정한다.
class AIProvider(Protocol):
    async def generate_reply(
        self,
        messages: list[ChatMessage],
        *,
        timeout_seconds: float,
        max_output_tokens: int,
    ) -> AIResult: ...

AIResult는 최소 text와 실제 model을 포함합니다. 토큰 사용량은 제공될 때 기록할 수 있지만 사용량이 없다고 답변 전체가 실패하도록 만들지 않습니다. 라우터는 HTTP 계약, 서비스는 처리 순서, provider는 외부 호출을 담당합니다. 문맥 구성·프롬프트는 순수 함수로 분리해 외부 API 없이 검증합니다.

3. 시스템 프롬프트 초안

너는 EasyExplain의 한국어 학습 도우미다.
사용자가 모르는 개념을 이해하도록 돕는다. 아는 척하거나 사실·출처를 지어내지 않는다.
서버가 지정한 설명 수준은 {level}이다.

처음 개념을 설명할 때는 다음 순서를 기본으로 한다.
1. 한 줄 정의
2. 수준에 맞는 설명 또는 비유
3. 짧은 예시
4. 핵심 정리

아주 쉽게: 일상적인 단어와 간단한 비유를 사용하고 생소한 용어를 풀어 쓴다.
입문자: 기본 용어를 정의한 뒤 작은 예시로 연결한다.
전공자: 필요한 전문 용어와 원리, 전제·한계를 포함하되 불필요하게 길게 쓰지 않는다.

후속 질문에는 같은 대화의 문맥을 활용한다.
“더 쉽게”, “예시 하나 더”, “핵심만”에는 요청한 형태로 답하고 매번 같은 서식을 강제하지 않는다.
질문이 모호하면 꼭 필요한 확인 질문 하나를 한다.
확실하지 않은 내용은 불확실성을 밝힌다. 실시간 검색을 했다고 말하지 않는다.
도구 실행·파일 접근·외부 검색 기능이 있는 것처럼 말하지 않는다.
현재 질문과 무관한 예전 설명을 반복하지 않는다.

범용 설명 포맷의 일관성은 프롬프트 품질 목표이지 모든 생성 결과가 반드시 준수한다는 보장은 아닙니다. 엄격한 JSON 응답을 추가해 복잡성을 늘리기보다 첫 버전은 일반 텍스트를 안전하게 표시합니다.

4. 문맥 전략

turn은 사용자 질문+완료된 AI 응답 한 쌍입니다. 최근 5턴은 최대 10개 메시지입니다. 현재 로그인 사용자 소유의 현재 conversation_id에서 status=completed인 것만 가져옵니다. 과거순으로 [user, assistant, user, assistant, ...] 배열을 만든 뒤 현재 질문을 마지막에 추가합니다. 현재 요청에서 선택한 level로 시스템 지침을 다시 생성합니다. 이전 level이 계속 적용되는 버그를 테스트합니다. 실패·pending 턴을 정상 assistant 답변처럼 컨텍스트에 넣지 않습니다.

입력 예산은 과거 대화 약 12,000자라는 간단한 추가 제한을 두고 초과하면 가장 오래된 Q/A 쌍부터 제외합니다. 이는 토큰 수와 동일하지 않습니다. 시스템 지침과 현재 질문을 보존하고, 선택 모델의 컨텍스트·출력 한도를 별도로 확인합니다. 첫 버전은 요약 메모리·벡터 검색을 구현하지 않습니다.

5. 호출 안정성

AI 총 대기시간 기본 30초, 브라우저 대기시간 기본 40초를 제안합니다. 배포 프록시 제한도 함께 확인합니다. SDK 자동 재시도가 총 시간/비용을 늘리지 않도록 자동 재시도는 끄거나 전체 데드라인 안에서 명시적으로 관리합니다. 초기 설계에서는 max_retries=0과 단일 요청 데드라인을 기본으로 하고, 무한 재시도하지 않습니다. 출력 토큰 기본 상한 800은 제안값입니다. 선택한 모델이 해당 옵션을 지원하는지 B가 실제로 검증합니다.

Fake provider는 정상 텍스트, 타임아웃, 상위 API 실패, 빈 응답을 재현할 수 있어야 합니다. 이런 테스트 모드는 테스트 의존성 주입/개발 설정으로만 사용하고 공개 API의 query/body 스위치로 노출하지 않습니다.
